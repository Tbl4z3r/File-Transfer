# Arquitectura e interfaces de implementación H1

Referencia normativa: `protocol/PROTOCOL.md`. Aprobada por Astra para paralelizar implementación una vez fijadas las herramientas por H0-COMPAT.

## Windows — tarea H1-WINDOWS

Propiedad `apps/windows/**`, reporte propio. Core Rust en `apps/windows/core/Cargo.toml`, libre de dependencias Tauri; thin shell Tauri en `apps/windows/src-tauri`, UI en `apps/windows`. Core: identidad/pair store persistentes; servidor HTTPS; estado de sesión y transferencias; stream/hash/temporales; acciones locales de recibir, aceptar/rechazar, ofrecer archivo a peer y revocar. Tauri/TypeScript llama comandos locales; nunca expone selección de rutas o administración por HTTP.

Comandos mínimos conceptuales (el binding Tauri puede adaptar nombres): `start_session(bind_ipv4, port)`, `stop_session()`, `open_pairing_window() -> descriptor`, `set_receive_enabled(bool)`, `list_peers()`, `revoke_peer(id)`, `accept_upload(id, destination)`, `offer_download(peer_id, source) -> Transfer`, `cancel(id)`, `get_transfer(id)`. `start_session` devuelve endpoint y pin; `open_pairing_window` es la única que devuelve token temporal. Las rutas remotas son exactamente las del contrato.

Preferir Rust rustls/rcgen, tokio, axum/hyper, sha2, rand/getrandom; fijar versiones comprobadas por compatibilidad y Cargo.lock. No custom verifier TLS que acepte todo. Certificado/key pair persistente fuera del repo. Un core ejecutable/testeable en Linux permite demostrar protocolo sin declarar compatibilidad Windows. Mantener el componente de servicio separable de dependencias GUI nativas para pruebas.

Aceptación: tests de parser con fixtures; servicio TLS real con pairing, bearer y autorización; subidas/descargas con digest; cancelación/revocación y rutas no atravesables; API estable para integrar Android. Compilar core/test en Linux disponible; build Windows queda separado y debe ejecutarse en Windows o CI Windows.

## Android — tarea H1-ANDROID

Propiedad `apps/android/**`, reporte propio. Kotlin/API28, cliente HTTP dedicado con pin+PKIX+hostname; resolvedor fijo para IP manual y host TLS fijo. Transporte Kotlin puro testeable en JVM, separado de Activity/Android Keystore mediante interfaces, para interoperabilidad loopback contra core Rust real. Pair store privado; descriptor manual; recibir oferta y aprobar; elegir archivo fuente y subir con content-length; bandeja privada o carpeta SAF elegida para descarga verificada; mostrar estados/progreso/errores. Sin Google Play Services, servidor Android ni mDNS H1. No `TrustAll`, `HostnameVerifier { true }`, fallback HTTP o desactivar TLS en debug.

Mantener Compose según matriz H0-COMPAT. Su dependencia gráfica transitiva contiene JNI: APK universal sin `abiFilters`, conservando los cuatro ABIs verificados del AAR, incluidos ambos ARM. No añadir TLS nativo. Inspeccionar ABIs del APK resultante; `adb shell getprop ro.product.cpu.abilist`, instalación y prueba en J4+ siguen pendientes antes de declarar compatibilidad real.

Interfaz central `ProtocolClient`: `pair(descriptor, deviceId, deviceName)`, `createUpload(name, size)`, `offers()`, `acceptDownload(id)`, `status(id)`, `uploadContent(id, stream, size)`, `downloadContent(id, sink)`, `complete(id, sha256)`, `cancel(id)`. Implementar digest mientras se leen/escriben bytes. En download consultar digest de servidor, validar/publicar, confirmar. UI y cliente deben permitir probar validadores JVM independientemente del dispositivo cuando sea posible.

Aceptación: mismo contrato/fixtures; rechazo de pin incorrecto y certificado inválido; credencial no expuesta; upload/download streaming con tamaños Long; autorización explícita; compilación APK si SDK disponible y pruebas JVM. APK compilado, emulador, instalación J4+, bloqueo de pantalla y rendimiento son evidencias distintas.

## Integración y límites

Prueba real deseada: emparejar manualmente, Android → Windows y Windows → Android, comparar hashes, registrar tamaño/segundos/MiB/s; probar recepción deshabilitada, revocación y pin incorrecto. Luego archivo >4 GiB en almacenamiento que lo permita. H1 no queda concluido sin Windows ↔ Android real y medición inicial documentada. Linux puede verificar interoperabilidad HTTP/TLS con cliente de prueba y contratos, no hardware.

Astra lee diffs reales y resultados antes de aprobar integración secuencial. Cualquier cambio de campo, ruta, validación TLS, límites o estados debe consultarse antes de implementarse. Implementadores pueden mejorar organización interna y pruebas sin alterar el contrato.
